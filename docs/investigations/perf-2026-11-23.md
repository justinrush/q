# q performance, 2026-11-23

## Why

q felt slow under heavy use on a work machine: the daemon once took longer to
come up than the client's 5s wait, and the board lagged. On that machine the
idle daemon was using **37% CPU** steadily (`ps`, 57 minutes after start, 146 MB
RSS) on v0.8.17-3 (e7f13c0, before 7c090e8's mutation speedups).

## What the work machine's state looks like

A copy of its `state.json`, `state-closed.json`, `events.ndjson*` and
`daemon.log`:

- **The board is small**: 22 missions not closed (19 in debrief, 3 briefing) and
  224 closed. But `state.json` is 2.5 MB and `state-closed.json` 3.5 MB.
- **Most of that is `codexUsage`**, the per-response checkpoint the Codex meter
  keeps (`mission.CodexUsage`): 1.54 MB of the hot file and 2.28 MB of the closed
  one. One rollout alone holds 4,071 responses, 1.24 MB.
- **The next largest is `toolHandoff`**: 821 KB hot, 410 KB closed, nearly all of
  it the handoff `conversation` (one is 442 KB).
- Everything else (prompts, usage, repos, analytics) is a few hundred KB.

The event log (6.2M lines, 471 MB, 2026-09-08 to 2026-11-23) says what the
daemon spends its writes on:

| label | count |
|---|---|
| `mission.runtime_status` | 5,218,352 |
| `mission.runtime_unavailable` | 877,820 |
| `mission.reconcile` | 87,417 |
| `mission.hook.pre-tool-use` | 19,907 |
| `mission.hook.post-tool-use` | 19,430 |
| `mission.usage` | 18,189 |
| everything else | < 5,000 |

The 1s runtime poll and the 15s reconciler dominate. Hooks are a small share.

Six of the hot missions are Codex missions in debrief. The runtime poll reads
each of them every second, and each read takes two whole-snapshot copies (one in
`reconcileCodexPlan`, one inside `MutateDeferred` before its function says
"unchanged"), on top of the poll's own copy. Measured against a copy of that
state, one idle tick took 36 ms and allocated 198 MB, almost all of it copying
usage maps: about 200 MB/s of garbage from a loop that, on an idle board, learns
nothing.

Process start is not a problem here: `q --version` is ~5 ms and a hook process
~6 ms (`scripts/bench-exec.sh`), and a hook's request to the daemon ~0.2 ms.

## What changed

Five commits, each measured by the benchmarks added first
(`go test -bench`, `missiontest.Work` and the real state via `Q_BENCH_STATE`):

1. **The Codex checkpoint stays off the wire.** Every stream frame and JSON reply
   carried each mission's `codexUsage`, which only the daemon's meter reads.
   Broadcasts with no board open are no longer encoded at all.
2. **Snapshot copies share usage values.** Usage, the Codex checkpoint and
   analytics records are never modified in place, so copies share them instead of
   deep-copying them; the types now say they must stay that way.
3. **Unchanged missions are not re-encoded.** The store keeps each mission's
   last encoding and reuses it while the mission is unchanged, and reuses a whole
   file none of whose missions changed. Output is byte-identical to
   `json.Marshal`.
4. **One mission is read without copying the board.** `Store.Mission` replaces
   25 `Snapshot().Mission(id)` calls, two of them on the 1s poll's path.
5. **Card text is cut in one pass.** `Truncate` was quadratic.

### Results

On the work machine's real state (`Q_BENCH_STATE`), median of 6 runs, Apple M4,
before the first fix and after the last (`benchstat`, all p=0.002):

| what | how often | before | after |
|---|---|---|---|
| idle runtime poll tick | every second | 36 ms, 198 MB | 2.4 ms, 16 MB |
| reconcile pass | every 15 s | 18.6 ms, 102 MB | 2.2 ms, 16 MB |
| snapshot copy | every read | 0.92 ms, 5.1 MB | 0.09 ms, 0.8 MB |
| deferred store write (PreToolUse, readings) | each change | 21 ms, 32 MB | 3.2 ms, 14 MB |
| synchronous store write | each Stop, status change | 29 ms, 33 MB | 12.6 ms, 14 MB |
| PreToolUse hook, daemon side | each tool call | 4.0 ms | 0.9 ms |
| Stop hook, daemon side | each turn end | 34 ms | 16 ms |
| `GET /v1/state` | board refresh, `q mission list` | 13 ms | 2.4 ms |
| first stream frame | each board connect | 12 ms | 2.4 ms |
| `/v1/health` | every q command, every hook | 1.1 ms | 0.19 ms |

On the `work` fixture (same shape, built), for the board:

| what | before | after |
|---|---|---|
| mission frame sent to the board | 250 KB, 0.58 ms | 2 KB, 5 us |
| board taking a snapshot frame (UI goroutine) | 30 ms | 3.1 ms |
| board taking a mission frame | 2.0 ms | 0.55 ms |
| redraw, rows layout | 12.8 ms | 1.05 ms |
| redraw, lanes layout | 1.5 ms | 1.3 ms |

End to end, a daemon run in a sandbox against a copy of the same state (no
peer, no reachable Codex app-server):

| | before | after |
|---|---|---|
| start to ready (handle written) | ~650 ms | ~300 ms |
| CPU over 60 s idle | 2.3 s (3.9%) | 0.5 s (0.9%) |
| RSS | 118 MB | 107 MB |

The sandbox's poll fails fast on the unreachable app-server, so it does less
work per tick than the work machine's; the benchmarks above model the reachable
case.

## Not done, in rough order of value

- **Measure the work machine itself.** Install this build there, then compare
  `ps -o %cpu` on the idle daemon with the 37% before, and take a profile under
  real load: `Q_PPROF=127.0.0.1:6061 q daemon restart`, then
  `go tool pprof -top 'http://127.0.0.1:6061/debug/pprof/profile?seconds=30'`.
  The sandboxed daemon here had no reachable Codex app-server, so the poll's
  per-mission RPCs and readings were not exercised; the profile will show
  whether they matter.
- **Move `codexUsage` and the handoff `conversation` out of `state.json`.**
  They are still 2.3 MB of the 2.5 MB hot file, so every synchronous write
  still writes them and each changed mutation still copies them. A per-mission
  sidecar file (`missions/<id>/codex-usage.json`, written by the meter) would
  shrink the hot file to ~200 KB. Needs a migration on `Open`.
- **Incremental transcript metering** (`internal/usage`, `scan`). A changed
  transcript is re-parsed from byte 0: 40 ms for a 10 MB one
  (`BenchmarkClaudeMeter`, `BenchmarkCodexMeter`), every 15s per running
  mission and on every turn end. The work machine has transcripts of 24 MB.
  Keep a byte offset and partial counts per file, as the Codex rollout observer
  already does.
- **The poll still copies the board inside each `MutateDeferred`**, even when
  its function decides nothing changed. A read-only precheck against
  `Store.Mission` (is the reading different from the card?) would skip the
  mutation for the commonest tick.
- **captureAnalytics clones and compares every mission's record on every
  mutation** (`analytics.go`), whatever changed. It could visit only missions
  the stamp found changed.
- **The board's first frame is still the whole board, closed missions
  included**, and decoding it takes ~3.5 ms on the UI goroutine. The board
  could ask for closed missions only when the done lane is open.
- **The board rebuilds all five lanes on every stream frame**
  (`Board.SetSnapshot`), and per card scans every mission for child counts and
  siblings. About 0.5 ms per frame on the work board: fine for now.
- **Reconcile asks tmux about each live mission separately** (`has-session`,
  `list-panes`). One `list-panes -a` per pass would do.
- **Hooks**: two loopback requests each (`/v1/health`, then the POST) and
  ~6 ms of process start (`scripts/bench-exec.sh`). Not worth changing unless
  the work machine's endpoint scanner makes process start much slower there;
  run the script on it to see.
